# Installer destination boundary, October 19, 2026

BF-B002 has a bounded local repair. The wizard and installer now share non-destructive destination validation before installed processes are closed or directories are created. Installation checks again after staging extraction and before replacing the destination.

Missing and empty destinations are allowed. An existing nonempty destination must contain a valid payload.manifest naming KillerPDF.App.exe. Every manifest payload file must exist with its recorded size and SHA-256. Unlisted files and directories are rejected. The only generated file allowed outside the manifest is KillerPDF.cmd with the exact content written by CommandLinePath.Register. Reparse points on the destination, its ancestors, and its children are rejected before any recursive traversal.

Registration inventory: pdf-file.ico is already in the installed payload list; registration writes KillerPDF.cmd beside it. Shortcuts and registry entries are outside the directory. Uninstall uses the installed executable with /uninstall, with no separate uninstaller copy. No normal per-user installed directory was present to inspect live. Synthetic manifest fixtures exercise validation only, not signed product recognition or installation.

Ranked hypotheses: (1) the existing path-only validation permits any nonroot work folder; (2) checking only manifest presence still accepts unrelated extra files; (3) the generated command wrapper can cause false rejection of ordinary upgrades; (4) junction aliases can evade direct-path checks.

The first slice extracted the existing permissive validation into ValidateInstallDestination, wired to the actual wizard and Install callers, with no ownership change. The regression script loaded the compiled launcher and called that internal production entry. It failed because a work folder containing customer-notes.txt was accepted. The sentinel hash stayed unchanged. An initial PowerShell argument-wrapping error was corrected before accepting that red result.

After the repair, the same command passed. The expanded 12-check matrix passed: unrelated sentinel rejected; missing and empty destinations accepted; verified synthetic payload accepted; exact command wrapper accepted; unrelated extra rejected; altered payload rejected; unrelated wrapper rejected; malformed manifest rejected; unknown empty directory rejected; target junction and a missing child below a junction rejected. The test never invokes the launcher entry point, installs, registers, or closes processes.

The final launcher build passed with zero warnings and errors. Its scratch source snapshot copied the launcher, Fonts, and Resources with existing bin/obj directories excluded. Program.cs SHA-256 matched the live source at 2E4BC4E5FFE9C0D5E1AD299C4B2011B25EDA2FF0F740C2050A971432E477EDC4; InstallerWizard.xaml.cs matched at FEF2B582D7E0E8A7920D531DA0DD14703CD9E0E235D8B3C48866CAD11288863C. Redirecting intermediate output against the live project initially exposed existing obj sources to WPF globs and failed with duplicate generated types; no unknown existing obj files were deleted. Building the isolated snapshot corrected that harness issue.

This is production validation evidence, not actual installation, upgrade, registration-failure rollback, or uninstall proof. Those still require authenticated guest execution, which is unavailable. Legacy directories without a manifest, damaged or locally modified payloads, and directories containing extra files refuse replacement and need a separate migration or repair decision. Refusal preserves unknown contents. Validation is a point-in-time check, not an atomic defense against a concurrent actor changing the directory after verification.
