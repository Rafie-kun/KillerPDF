# Issue 437 crash report followup

October 19, 2026. [Issue 437](https://github.com/SteveTheKiller/KillerPDF/issues/437) remains open. Authenticated issue and comment reads succeeded. No comment, label, issue state, branch, or release was changed.

The new report is from KillerPDF 1.8.91 and shows UCEERR_RENDERTHREADFAILURE, HRESULT 0x88980406, while WPF handles a resize during restoration. The live thread describes maximized-only failures from Win+D or taskbar minimize/restore, with no PDF required. The original reporter reproduced on Intel systems at 150% scaling; the new reporter describes an AMD system at 200%. An active Open PDF dialog reportedly avoids the problem. These observations point toward the main window's native transition/composition path, without proving one specific cause.

## Verified code gap

The 1.8.91 tagged source and current 1.8.92 checkout both branch on managed WindowState in `Shell/WindowChrome.cs` when calculating the maximized client rectangle. They clamp the proposed rectangle to monitor bounds without checking for a nonpositive intersection.

The 1.9 branch already has commit 086b8d3 from October 14. Its corresponding handler skips iconic windows, uses native IsZoomed state, and declines invalid intersections. That commit is present in the 1.8 repository's object database but not applied to its current main source. This is a verified source difference, not evidence that the new reporter has tested the guarded behavior.

For an offscreen minimized rectangle, the old clamp can calculate a left/top coordinate at the monitor origin while its right/bottom coordinates remain offscreen. A nonpositive client size is therefore a concrete candidate mechanism. The actual reporter crash has not been reproduced here, so this review does not promote that mechanism to confirmed cause.

## Ranked next checks

1. A native/managed state transition mismatch permits invalid client geometry. Capture actual WM_NCCALCSIZE input/output during maximized minimize/restore and compare the guarded candidate.
2. Native DWM/WPF hardware composition fails even with valid client rectangles. Compare hardware and software WPF rendering in separate launches on an affected system.
3. The modal picker changes owner activation or animation timing. Compare equivalent restore sequences with and without the picker while logging geometry and native state.

The application currently marks Dispatcher exceptions handled and queues a WPF recovery dialog. That behavior should be reviewed for render-thread failures separately; treating every such failure as recoverable is not a demonstrated recovery mechanism.

[Microsoft's render-thread diagnostic article](https://learn.microsoft.com/en-us/troubleshoot/developer/dotnet/framework/general/wpf-render-thread-failures) explains that SyncFlush stacks identify the observed failure category, not the underlying failing graphics call. It recommends hardware/software comparison during diagnosis. The article targets .NET Framework 4.8; it is diagnostic background, not proof of a .NET 10-specific cause or fix.

No UI or GPU reproduction ran. No speculative chrome or global rendering-mode change was made. The supplied log contents were reviewed; the linked attachment fetch was unavailable through the browser text fetcher. Genuine maximized minimize/restore acceptance is still required before claiming this issue fixed.
